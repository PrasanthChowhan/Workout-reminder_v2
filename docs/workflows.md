# GitHub Actions CI/CD Workflows

This document outlines the Continuous Integration (CI) and Release (CD) workflows configured for Kodon.

---

## 🛡️ Continuous Integration (CI)

The CI workflow is configured in [ci.yml](file:///E:/00_HeadQuaters/50_Projects/Workout%20reminder_v2/.github/workflows/ci.yml).

- **Triggers**: Automatically on every `push` and `pull_request` targeting the `main` branch.
- **Jobs**:
  1. **test-frontend (Linux)**: Installs dependencies, sets up Node.js, and runs the Vitest suite (`npm run test`).
  2. **check-backend (Linux & Windows)**: Sets up the Rust toolchain, installs system build dependencies (on Linux), configures compiler caching (`swatinem/rust-cache`), and runs `cargo check` and `cargo clippy -- -D warnings`.

This workflow ensures that code changes are stable and compile cleanly across platforms before they are merged.

## 🚀 App Releases & Beta Builds (CD)

The Release workflow is configured in [release.yml](file:///E:/00_HeadQuaters/50_Projects/Workout%20reminder_v2/.github/workflows/release.yml).

- **Triggers**: Automatically when you push any version tag starting with `v` (e.g. `v0.1.0` or `v0.1.0-beta.1`).
- **Platforms**: Packages installers for both **macOS** and **Windows** (`macos-latest`, `windows-latest`).

### Dynamic Build Modes

The workflow automatically detects if the tag is a release candidate or beta build:

| Tag Format | Example | Release Status | GitHub Release Draft Status |
| :--- | :--- | :--- | :--- |
| **Beta / RC** (contains `beta` or `rc`) | `v0.1.0-beta.1` | **Pre-release** | Published immediately |
| **Stable Production** | `v0.1.0` | **Stable** | Saved as a **Draft** (manual publish required) |

### How to Release a New Version

1. Make sure your local repository is up to date and your working tree is clean.
2. Create and push the appropriate tag:

   **For Beta Builds:**
   ```bash
   git tag v0.1.0-beta.1
   git push origin v0.1.0-beta.1
   ```

   **For Production Releases:**
   ```bash
   git tag v0.1.0
   git push origin v0.1.0
   ```

3. Go to the **Actions** tab on your GitHub repository page to watch the builds progress.
4. Once completed, your installer assets (`.exe`/`.msi` for Windows, `.dmg` for macOS) will be uploaded directly to the GitHub Releases page under the matching tag.

## 🔑 Required Repository Secrets

To sign and build release binaries successfully, make sure the following secrets are configured under your GitHub Repository Settings (**Settings > Secrets and variables > Actions > Repository secrets**):

1. **`TAURI_SIGNING_PRIVATE_KEY`**: Your private signing key generated by Tauri (required for updating/signing builds).
2. **`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`**: The password associated with your Tauri private signing key.
3. **`GITHUB_TOKEN`**: Provided automatically by GitHub Actions, used to write releases.
